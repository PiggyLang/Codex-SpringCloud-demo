# 阶段九：接入 Sentinel 熔断

历史提交：`4519a4675996ae7b4f0a9a958ac8ea480e9ce301`。

本文记录该提交对应的历史快照和当时的验证方式。当前项目可能已在后续提交中继续演进；请以当前源码及配置为准启动完整项目。

订单服务只为 `order -> UserClient.getUser(100L)` 设置 Sentinel 熔断资源 `user-info`。正常响应仍包含用户信息；Feign 异常、用户服务空响应和 Sentinel 熔断拦截仍返回 HTTP 200，状态为 `UNAVAILABLE`，并省略 `user` 字段。其他编程错误继续向外暴露。Sentinel Web filter 已关闭，因此不会把整个 `/orders` 路由也纳入资源统计。

本地规则在订单服务启动时加载，使用异常比例策略：错误比例阈值 `0.5`，最少请求数 `5`，统计窗口 `30` 秒，熔断时长 `10` 秒。规则只存在于当前进程内存中，重启订单服务会重新开始统计；暂未配置 Sentinel Dashboard、Nacos 规则持久化或其他规则源。它们是方便观察的教学值，不是生产环境建议。OpenFeign 连接和读取超时仍分别是 1 秒和 2 秒，也不是整个订单请求的总耗时上限。

## 本地观察

启动 Nacos、网关、订单服务和用户服务。修改配置或代码后重启订单服务。经网关发起正常请求：

```text
GET http://localhost:18080/orders/1
```

响应包含 `user`、`userStatus: AVAILABLE` 和 `userMessage: 查询成功`。要稳定观察熔断，可以先停止用户服务两个实例（端口 `18081` 和 `18083`），再重启订单服务，使错误窗口从干净状态开始。随后在 30 秒内至少请求 5 次。前 5 次仍会尝试调用用户服务；异常比例达到阈值后日志会显示资源进入 `OPEN`。接下来的请求仍返回订单降级 JSON，但会记录“调用被熔断拦截，直接返回降级结果”，而且不会出现“调用用户服务查询用户 100”的实际调用日志。

降级响应保持原有 JSON 合同：

```json
{
  "orderId": 1,
  "productName": "Java 面试题",
  "userStatus": "UNAVAILABLE",
  "userMessage": "用户信息暂不可用"
}
```

重新启动一个用户服务实例，等待 Nacos 服务发现更新，并等待熔断窗口的 10 秒结束。下一次订单请求会成为 `HALF_OPEN` 探测：成功时日志显示 `HALF_OPEN -> CLOSED`，后续请求恢复正常；失败时会重新进入 `OPEN`。观察订单服务的实际调用日志和 Sentinel 状态切换日志，才能判断是否发生了熔断；仅凭停止状态的用户服务没有输出日志，不能证明订单服务停止了远程调用。Sentinel 在 OPEN 期间阻止再次调用，不能理解为整个订单请求的通用、无条件耗时上限。

此演示固定查询用户 `100`，不定义“用户不存在”状态。服务成功返回“用户不存在”时，应由业务规则决定如何展示，不要和远程服务暂时不可用混为一谈。
